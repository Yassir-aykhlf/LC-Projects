
# Password reset workflow

## What you should know

Mode: Debugging.

You should be comfortable with environment variables, timezone-aware datetimes, and updating state through a storage API. Use Python 3.12 and the standard library. The public tests need no package installation.

---

## Scenario

Users report that reset codes expire incorrectly and passwords sometimes remain unchanged after a successful response. The service also rewrites its configured authentication URL and accepts some codes more than once. Repair the workflow in `auth_service.py`.

The supplied database is an in-memory mock. The URL is configuration data; this exercise sends no HTTP requests or email.

## Public API

```python
class PasswordResetService:
    def __init__(self, *, clock=None): ...
    def request_reset(self, user_id: str) -> str: ...
    def verify_and_reset(self, user_id: str, code: str, new_password: str) -> bool: ...
```

Import the class from `auth_service.py`. Its `auth_service_url` attribute exposes the configured URL.

`clock`, when supplied, is a zero-argument callable returning a timezone-aware `datetime`. Use it to obtain the current time in both operations. When omitted, use the current UTC time. The clock can move backwards; its output is otherwise valid. Do not read it during construction or when rejecting a request for an unknown user.

## Requirements

### 1. Configuration

- Read `INTERNAL_AUTH_URL` once when constructing each instance.
- If the variable is absent, use exactly `http://internal.auth.local`.
- If it is present, preserve its value exactly, including an empty value or surrounding whitespace. Do not rewrite, validate or contact the URL.
- Later environment changes affect new instances only. Construction must not change database state.

### 2. Request a reset

- `request_reset` first checks that the user exists. Otherwise, raise `ValueError("User not found")` without creating or changing any state.
- For a known user, generate and return a nonempty string code. Values generated by one service instance must not repeat, including after successful use. No fixed length or alphabet is required.
- The new code must also differ from that user's currently stored code, even if another service instance issued it.
- Save the returned code and the current time through `db.save_reset_code`. Store the time as a timezone-aware UTC `datetime` representing the same instant as the clock value.
- A second request replaces that user's existing code and creation time. It starts a new 30-second validity window. Requesting a reset does not change any password or another user's state.

### 3. Verify the code and time

- Return the boolean `False` if the user does not exist, has no reset record, or supplies a code that does not match exactly. Do not trim or otherwise normalize codes.
- Existing records contain a string `code` and a valid `datetime` named `created_at`. A timezone-aware timestamp can use any UTC offset. Interpret a legacy timestamp without timezone information as UTC.
- Let `age` be the elapsed seconds from `created_at` to the current clock value, comparing instants rather than local clock fields. A matching code is valid only when `0 <= age < 30`.
- Age `0` and age `29.9` are valid. Age `30` is expired. A negative age is invalid because the stored timestamp is in the future.
- Any verification that returns `False` leaves all passwords and reset records unchanged. An incorrect attempt must not consume a valid code; an expired record may remain stored until a later request replaces it.

### 4. Save the password

- For a known user with a matching, valid code, persist exactly `"hashed_" + new_password` through the database boundary.
- `new_password` is a string and must be preserved exactly. Empty strings, whitespace and Unicode are allowed; password-strength rules are outside this exercise.
- `hashed_` is a mock transformation for this problem, not a real password-hashing scheme.
- `db.get_user` returns a copy. Changing that dictionary does not save a password. Use `db.update_password` and preserve the user's email and other profile fields.
- Check user existence at verification time. A leftover reset record for a deleted user must return `False` without changing state.

### 5. Consume the code and isolate users

- After a successful password update, clear that user's reset record through `db.clear_reset_code`, then return the boolean `True`.
- Replaying that code must return `False`, including through a different service instance. A later reset request must issue a new code and allow another password change.
- Codes belong to the user whose reset record stores them. Do not reset one account using another account's code or clear another user's record.

### 6. Storage boundary and scope

- Use the shared `db` object from `database.py`. Different service instances share its saved users, passwords and reset records. Do not replace it with instance-local storage or mutate its private dictionaries from service code.
- The database methods are `get_user`, `update_password`, `save_reset_code`, `get_reset_code` and `clear_reset_code`. The initial mock user is `user_123`; tests provide isolated fixtures with additional users.
- Arguments are strings; user identifiers are compared exactly. Behavior for non-string arguments or malformed database records is not graded.
- Calls are sequential. Concurrent verification, transactions, attempt limits, code hashing and durable storage are reflection topics, not required implementation work. Keep the database's existing raw-code interface for this exercise.
- Use only the Python standard library. The service must run without network access or external services.

## Implementation checklist

Each task is required.

1. Repair configuration loading and preserve explicit environment values.
2. Generate fresh codes and save their UTC creation times.
3. Enforce the exact validity window, including legacy timestamps and timezone offsets.
4. Persist password changes and handle missing or deleted users.
5. Consume successful codes, replace older requests and keep users isolated.
